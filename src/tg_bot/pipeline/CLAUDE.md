# pipeline/ — LLM execution hot path

In the hot path between "user taps ticker" and "LLM result ready." Modules that build/run/cache LangGraph propagation.

See root `CLAUDE.md` for the request lifecycle (lines 66–83), state ownership table, and Invariants #1, #2, #5, #6 — all relevant here.

## Key contracts

- **`TRADINGAGENTS_AVAILABLE`** flag gates analysis; bot still loads if tradingagents fails to import.
- **`AnalysisConfigKey` is the source of truth for config identity.** Frozen dataclass `(provider, deep, quick, rounds, effort)` emitting three shapes: `slug()` → cache dir (`provider__deep__quick[__r{n}][__e{level}]`), `caption()` → caption "via" line (`provider · deep/quick [· r{n}] [· e={level}]`), `telegraph_title(ticker)` → page title (`<TICKER> Analysis · <caption>`). Also the GraphPool dict key — hashability via `frozen=True`. Constructed once per request and threaded into cache, caption, Telegraph publish. `from_config(config)` iterates `EFFORT_KEY_BY_PROVIDER.values()` so the per-provider effort key (`openai_reasoning_effort` / `anthropic_effort` / `google_thinking_level`) resolves without the dataclass knowing the mapping. Invariant #1 (root) lists the four edits needed when adding a knob.
- **Graph pool.** `analysis.py:_graph_pool` keeps a `GraphPool` per `(provider, deep, quick, rounds, effort)` key — the 5-tuple matches the cache slug knobs so two users on different rounds/effort don't share an instance baked with the wrong config. Each pool grows lazily up to `Config.MAX_CONCURRENT_ANALYSES` `TradingAgentsGraph` instances; `pool.acquire()` returns the first free one (or builds a new one outside the mutex if under cap, or blocks on `queue.Queue.get()` if at cap — but the per-key cap matches the global asyncio semaphore so the blocking branch is unreachable). Each instance is single-use-at-a-time because the graph mutates `self.ticker / self.curr_state` during `propagate()`, but the pool gives us both parallelism (different instances run concurrently) and caching (instances are returned to the pool on completion). Don't bypass `_get_or_create_pool`. Key-level LRU at `GRAPH_CACHE_MAX` (default 4) — evicting drops the entire pool for that key.
- **Per-step progress + cooperative cancel.** `progress.py:delegating_progress_callback` is a singleton `BaseCallbackHandler` attached to every graph via `callbacks=[...]` in the constructor. **`raise_error = True` on this class is load-bearing** (Invariant #2): LangChain's callback manager swallows handler exceptions by default, defeating our raise-to-cancel strategy. With it enabled, raising `CancelledByUserError` from `_dispatch` aborts the about-to-fire LLM call and bubbles up through langgraph → `propagate()` → `to_thread`. TradingAgents passes our callbacks into the LLM kwargs, so we receive `on_chat_model_start` / `on_llm_start` events — **not** `on_chain_start`. LangGraph propagates the surrounding node name as `metadata["langgraph_node"]` on every nested LLM call. Per-run target (`ProgressReporter`) lives in `threading.local()` set by `run_trading_analysis` around `propagate()`. `ProgressReporter.cancel_event: threading.Event` is checked in `_dispatch` BEFORE every step update; the reporter also re-attaches the ❌ Cancel keyboard on every caption edit (Telegram drops `reply_markup` if not re-sent on `editMessageCaption` — Invariant #3).
- **Same-day result cache.** `cache.py` is filesystem-backed, keyed on `(AnalysisConfigKey, ticker, date_iso)` — no `user_id`, so two users on the same `/config` share results within a day, and a manual `/watch` + same-day digest fire only pay for one LLM run. Public API: `lookup` / `store` / `today_iso()`. Layout: `<TG_BOT_DATA_DIR>/result_cache/<key.slug()>/<TICKER>/<date>.json`. Atomic writes (tempfile + fsync + rename, same pattern as `JsonStorage._save`); tempfile is `unlink`'d on any write exception. Each entry persists `{final_state, signal, telegraph_url, generated_at}` — full `final_state` (not a slim shape) so future renderer changes don't require re-running every cached ticker. LangChain message objects in `final_state` aren't JSON-native; `cache._json_default()` coerces via `model_dump` → `dict` → `{__type__, content}` → `{__type__, repr}` (Invariant #6). **Cache-hygiene gate is built into `cache.store`**: a falsy `telegraph_url` is a no-op (logged + skipped) — caching a failed publish would trap the user replaying "Instant View unavailable" until midnight rollover. Lazy eviction: a fresh date for the same `(key, ticker)` sweeps stale-date siblings **after** the atomic write succeeds, so a mid-write failure can't orphan yesterday's still-valid entry.
- **`from_config` effort resolution is first-truthy-wins across providers (`config_key.py:75-78`, `analysis.py:298-302`).** Iterates `EFFORT_KEY_BY_PROVIDER.values()` in insertion order (`openai_reasoning_effort` → `anthropic_effort` → `google_thinking_level`) and returns the first key whose value is truthy. If a user has a stale provider's effort key still in their config dict (provider switch didn't fully wipe), the wrong provider's value is silently used. Today this is safe because `set_llm_provider` wipes deep/quick and `clear` wipes all LLM keys — but a hand-edited `user_config.json` with two providers' effort keys present will misattribute. If a future provider's key is alphabetically before openai's in iteration, that becomes the new winner.
- **`_json_default` per-object fallback is silent (`cache.py:105-114`).** The fallback chain `model_dump → dict → {__type__, content} → repr` catches all exceptions at each step and falls through. There's no per-object log when a pydantic model raises mid-`model_dump` — only the outer `cache.store` emits a warning if the entire `json.dump` raises. A partially-coerced `final_state` writes successfully but renders garbage on cache-hit. If diagnostics around cache reads ever get noisy, add per-fallback DEBUG logs first.
- **`ProgressReporter` is `threading.local`, set by `run_trading_analysis` around `propagate()` (`progress.py:50,195`).** If a langgraph node ever spawns a sub-thread (e.g. a tool node using `ThreadPoolExecutor`), the child has no `_current_reporter.value`, so `_dispatch` silently drops cancel checks on any LLM calls fired from it. Today no node does this, but tradingagents upgrades could change that; the symptom would be "Cancel doesn't stop the run for the duration of one node" without any error.
- **`cache.lookup` corrupt-file path is non-self-healing (`cache.py:132-139`).** Returns `None` on any exception — including `JSONDecodeError` from a half-written or hand-edited file. The corrupt file is NOT deleted at lookup time, so every same-day re-tap forces a fresh LLM run while the bad file persists. It only gets removed by the stale-sweep on the next-day `store` for the same `(key, ticker)`. Symptom: one slug+ticker+date burning credits in a loop until midnight rollover.
- **`_try_acquire_nonblocking` lives in `handlers/analysis_runner.py`, NOT pipeline.** Root CLAUDE.md "Known limitations" mentions it — that helper reads `sem._value` / `sem._waiters` private attributes for instant-reject of full-semaphore acquires. It's not a pipeline concern; documented here to redirect future searches.
- **`GRAPH_CACHE_MAX` is floored at `Config.MAX_CONCURRENT_ANALYSES` (`analysis.py:99`).** Defined as `max(8, 2 * Config.MAX_CONCURRENT_ANALYSES)` so an evicted pool can never hold an in-use instance: with N concurrent runs across N distinct configs and the cache capped below N, the first-evicted pool's `finally: self._q.put(graph)` would return the in-flight instance to a queue belonging to a dropped pool — silent leak. The 2× multiplier gives headroom for `/config` churn (provider/depth switches) so a user toggling between 2–3 configs in a session doesn't thrash ~500ms rebuilds (LangChain client + ChromaDB init). Floor of 8 covers the default `MAX_CONCURRENT_ANALYSES=3` case where 2×=6 still felt tight under multi-provider experimentation; memory cost is ~30–60 MB per cached pool, so the cap holds total memory bounded. Don't drop below `Config.MAX_CONCURRENT_ANALYSES` without re-proving the invariant.
