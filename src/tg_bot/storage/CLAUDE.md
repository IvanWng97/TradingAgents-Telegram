# storage/ — JSON persistence

Terminal in the dependency DAG: imports no `tg_bot.*` modules upward. Owns a `JsonStorage` subclass or its singleton. New storage classes inherit `JsonStorage`.

See root `CLAUDE.md` for cross-cutting invariants (esp. #8 storage mutations, #10 ticker normalization).

## Key contracts

- **Storage singletons** live in `tg_bot.storage` — both handler modules import the same `watchlist_storage` / `user_config_storage` so writes are immediately visible everywhere. Don't construct your own `WatchlistStorage()` / `UserConfigStorage()` in handlers.
- **Watchlists are stored sorted.** `WatchlistStorage._load` sorts each user's list (case-folded dedup → `sorted()`) on read, and `add_ticker` re-sorts after appending, so `/watch`, `/digest` ticker picker, `/del`, and `/history` ticker list all see stable alphabetical order without sorting at the call site. Existing pre-sort saves are upgraded transparently on the next `add_ticker`. `remove_ticker` preserves order naturally.
- **Storage mutations are async + atomic + durable.** `add_ticker`, `remove_ticker`, `set_digest_hour`, `set_digest_tz`, `set_digest_tickers`, `disable_digest` are `async def` and call `await self._save_async()`. `_save` writes to a tempfile in the same directory, `flush + fsync`s the file descriptor, then `os.replace`s into place — survives mid-write power loss. Read methods (`get_*`, `iter_*`) stay sync — pure in-memory dict reads.
- **Per-user config** lives in `data/user_config.json`, keyed by stringified Telegram user_id. **Digest-only** post-refactor: holds an optional `digest: {enabled, hour_local, tz, chat_id, tickers: list[str]}` block — `tickers` is the digest filter (explicit opt-in, default `[]` for new users, fan-out skips with a reminder when empty). LLM provider / deep / quick / rounds / effort fields are NOT stored here anymore — the active LLM config is process-wide and resolved from `.env` via `tg_bot.pipeline.analysis.build_config()` (see `pipeline/CLAUDE.md`). Legacy entries with stale `llm_*` keys are tolerated by `_load` (json.load just ignores unknown fields at the storage layer) but ignored at run time; they can be hand-pruned by deleting those keys.
- **`get_enrolled_tickers(user_id, watchlist)`** is the single canonical evaluator for "what tickers does this user's digest fire today" — used by `run_user_digest` (the source of truth) and `/list`'s text view (via `_digest_enrolled_set`). Handles the legacy-fallback ("`tickers` key absent" → all watchlist) + intersection with live watchlist. Deliberately does NOT gate on `enabled` — callers add that check themselves where the "off entirely" copy diverges from "enabled but empty enrolment".
- **Corrupt-JSON recovery is two-tier (`_base.py:30-58`).** On `JSONDecodeError`, `_load` renames the file to `<name>.corrupt-<unix_ts>` (warning logged), state resets to `{}`, and the bot keeps running. If the rename itself fails (`OSError`), the corrupt original stays in place and the next `_save` will overwrite it with `{}` — an `logger.error` is emitted explicitly stating this. Backups are never cleaned up; operators must sweep `data/*.corrupt-*` manually. Subclasses that hold structurally-required data should consider gating writes on a fresh-load sanity check after a corrupt-recovery event.
- **`_save_async` thread-safety has a no-await-between-mutation-and-save rule (`_base.py:92-100`).** Only the disk I/O is offloaded; `self._data` mutations must be serialized by PTB's event loop. The current safety property is that no other coroutine runs between a `self._data[...] = x` and the subsequent `await self._save_async()` because there's no yield point. If a subclass ever inserts an `await` between them, concurrent writers can race and silently lose each other's changes. New subclass methods that mutate-then-await-then-save are an antipattern here.
- **Tempfile naming → multi-instance silent-write-loss.** `_save` writes `<name>.<random>.tmp` in the same directory then `os.replace`s. Two processes pointed at the same `data/` (e.g., two containers on a shared bind mount) have no file lock — `os.replace` is atomic on POSIX, so one rename wins and one is silently discarded. Single-instance only. Document this in deploy notes if multi-replica is ever considered.
- **`set_digest_tickers` raises `TypeError` on non-list inputs — intentional asymmetry with peer setters (`user_config.py:257-260`).** Peer setters (`set_digest_hour`, `set_digest_tz`) validate user-supplied data and return `False` on bad input. This one guards a **programming error**, not user input: passing a bare string like `"NVDA"` would iterate characters and silently store `["N","V","D","A"]`. The TypeError is loud-by-design so the bug surfaces in tests instead of corrupting data. All current callers pass lists; if a future caller threads user input through here, validate at the call site, don't downgrade this to `return False`.
- **`iter_users_with_digest` vs `iter_enabled_digests` (`user_config.py:278-293`).** The former walks ALL users with a `digest` block (enabled or not) — input to `_post_init`'s backfill loop. The latter is the scheduling input. Mixing them re-registers jobs for disabled users; verify which one you need before calling.
- **`remove_ticker` prunes the user key entirely when the list empties (`watchlist.py:43-44`).** `get_watchlist` still returns `[]` either way, so the user-facing surface is unchanged. But future code that keys "has the user ever used the bot" on watchlist-presence will incorrectly answer no after they delete their last ticker.
